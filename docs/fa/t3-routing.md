# t3-routing

سیاست مسیریابی مدل برای کسانی که Claude Code را داخل T3 Code اجرا می‌کنند: thread اصلی ارزان می‌ماند و کار واقعی با `delegate_task` به مدل مناسب سپرده می‌شود. این یک افزونه نیست؛ یک سیاست است که در `CLAUDE.md` می‌گذارید و مدل از آن پیروی می‌کند.

[prompt-router](prompt-router.md) هر پرامپت را با قواعد به یک مدل می‌فرستد. t3-routing برای هر کار تصمیم می‌گیرد که داخل خود thread انجام شود، به یک فرزند سپرده شود یا council تشکیل شود؛ آن هم با فهرست مدل‌هایی که خود T3 گزارش می‌دهد. هر دو را می‌شود با هم استفاده کرد.

## نصب

۱. فایل `~/.claude/CLAUDE.md` (یا `CLAUDE.md` پروژه) را باز کنید.
۲. محتوای [CLAUDE-snippet.md](../../t3-routing/CLAUDE-snippet.md) را به انتهای آن اضافه کنید.
۳. جدول را ویرایش کنید: نام ردیف‌ها را با مدل‌هایی که `orchestrator_capabilities` برای حساب شما نشان می‌دهد عوض کنید و مدل‌های حذف‌شده را بنویسید.

فقط جایی اثر دارد که ابزارهای T3 (`delegate_task` و `orchestrator_capabilities`) وجود داشته باشند.

## روش کار

- **شروع نشست:** ابتدا فهرست زندهٔ مدل‌ها خوانده می‌شود؛ شناسهٔ مدل هرگز ثابت نوشته نمی‌شود.
- **triage:** کار کوچک یا وابسته به زمینهٔ نشست داخل thread می‌ماند؛ وگرنه یک فرزند، حداکثر دو فرزند هم‌زمان و بدون واگذاری تودرتو.
- **جدول مسیریابی:** از ردیف ارزان شروع کنید و فقط با شکست بررسی یا ابهام واقعی بالا بروید.
- **council:** کم‌یاب، فقط‌خواندنی و یک دور؛ برای معماری، امنیت، تغییر بازگشت‌ناپذیر یا ریشه‌ای که بعد از یک رفع ناموفق هنوز معلوم نیست.
- **قواعد:** push فقط از thread اصلی و پس از بازبینی و تست؛ رمز و زیرساخت production هرگز واگذار نمی‌شود.

## چه کاری به کدام مدل، چرا و با چه effort

نگاشت فعلی نویسنده به‌عنوان نمونه (نام مدل‌ها زود کهنه می‌شود؛ ردیف‌ها را با فهرست `orchestrator_capabilities` خودتان جایگزین کنید):

| کار | مدل (نمونه) | effort | چرا |
| --- | --- | --- | --- |
| ویرایش مکانیکی، فرمت، تغییر نام | gpt-6-luna | low | مشخصات دقیق است و استدلالی لازم نیست؛ ارزان‌ترین ردیف کافی است |
| جست‌وجو، فهرست‌برداری، خلاصهٔ لاگ | gpt-6-luna (جایگزین Haiku 5.5) | low / medium | خواندن زیاد و ریسک کم؛ زمینهٔ thread اصلی تمیز می‌ماند |
| تست، fixture، پیش‌نویس مستندات | gpt-6-luna، بعد gpt-6-astra | medium | کمی قضاوت لازم است؛ فقط بعد از یک شکست ردیف بالاتر |
| feature، backend، بازآرایی | gpt-6.1-sol (جایگزین Sonnet 5.5) | medium، با شکست بررسی high | منطق واقعی دارد، ولی شکست بررسی ارزان‌ترین نشانه برای خرج بیشتر است |
| دیباگ سخت، معماری، امنیت، DB/RLS | gpt-6.1-sol (جایگزین Opus 5.5) | high؛ xhigh فقط بعد از یک تلاش ناموفق | اشتباه گران است؛ thread اصلی نتیجه را بازبینی می‌کند |
| ساخت UI | gpt-6.1-sol (جایگزین Sonnet 5.5) | high؛ xhigh فقط برای سیستم طراحی جدید | کیفیت بصری به قوی‌ترین مدل و مهارت‌های طراحی نام‌برده نیاز دارد |
| بررسی بصری UI | Sonnet 5.5 + خودکارسازی مرورگر | medium، حداکثر ۲ دور | حلقهٔ ارزان و محدود؛ از صیقل بی‌پایان جلوگیری می‌کند |
| بازبینی diff | gpt-6.1-sol با زمینهٔ تازه، فقط‌خواندنی | high | بازبین بدون زمینهٔ نویسنده؛ برای امنیت/داده، خانوادهٔ مدل متفاوت از نویسنده |
| council | gpt-6.1-sol + Sonnet 5.5 (Opus فقط برای حساس‌ترین) | xhigh + high | دو خانواده، یک دور، فقط‌خواندنی؛ کم‌یاب |
| رمزها، زیرساخت production، کار بازگشت‌ناپذیر | فقط thread اصلی | — | هرگز واگذار نمی‌شود |

**انتخاب effort:** از پایین‌ترین effort مجاز آن ردیف شروع کنید؛ فقط با شواهد (شکست بررسی پذیرش یا ابهام واقعی) یک پله بالا بروید، نه به‌خاطر طولانی بودن یا مهم به‌نظر رسیدن پرامپت. دو شکست روی یک کار یعنی مدل جایگزین و شکست سوم یعنی thread اصلی. effort از نوع `max`/`ultra`، حالت fast و سطح سرویس priority خاموش‌اند مگر خودتان بخواهید (priority فقط وقتی منتظر فرزند مسیر بحرانی هستید).
