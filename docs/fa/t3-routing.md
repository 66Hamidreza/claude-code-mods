# t3-routing

سیاست مسیریابی مدل برای کسانی که Claude Code را داخل T3 Code اجرا می‌کنند: thread اصلی ارزان می‌ماند و کار واقعی با `delegate_task` به مدل مناسب سپرده می‌شود. این یک افزونه نیست؛ یک سیاست است که در `CLAUDE.md` می‌گذارید و مدل از آن پیروی می‌کند.

[prompt-router](prompt-router.md) هر پرامپت را با قواعد به یک مدل می‌فرستد. t3-routing برای هر کار تصمیم می‌گیرد که داخل خود thread انجام شود، به یک فرزند سپرده شود یا council تشکیل شود؛ آن هم با فهرست مدل‌هایی که خود T3 گزارش می‌دهد. هر دو را می‌شود با هم استفاده کرد.

## نصب

۱. فایل `~/.claude/CLAUDE.md` (یا `CLAUDE.md` پروژه) را باز کنید.
۲. محتوای [CLAUDE-snippet.md](../../t3-routing/CLAUDE-snippet.md) را به انتهای آن اضافه کنید.
۳. جدول را ویرایش کنید: نام ردیف‌ها را با مدل‌هایی که `orchestrator_capabilities` برای حساب شما نشان می‌دهد عوض کنید و مدل‌های حذف‌شده را بنویسید.

فقط جایی اثر دارد که ابزارهای T3 (`delegate_task` و `orchestrator_capabilities`) وجود داشته باشند.

## روش کار

- **شروع نشست:** ابتدا فهرست زندهٔ مدل‌ها خوانده می‌شود؛ شناسهٔ مدل هرگز ثابت نوشته نمی‌شود.
- **triage:** کار کوچک یا وابسته به زمینهٔ نشست داخل thread می‌ماند؛ وگرنه یک فرزند، حداکثر دو فرزند هم‌زمان و بدون واگذاری تودرتو.
- **جدول مسیریابی:** از ردیف ارزان شروع کنید و فقط با شکست بررسی یا ابهام واقعی بالا بروید.
- **council:** کم‌یاب، فقط‌خواندنی و یک دور؛ برای معماری، امنیت، تغییر بازگشت‌ناپذیر یا ریشه‌ای که بعد از یک رفع ناموفق هنوز معلوم نیست.
- **قواعد:** push فقط از thread اصلی و پس از بازبینی و تست؛ رمز و زیرساخت production هرگز واگذار نمی‌شود.

## چه کاری به کدام مدل، چرا و با چه effort

ردیف‌ها: **P-F / P-W** = مدل سریع / کاری provider اصلی؛ **C-F / C-W / C-D** = مدل سریع / کاری / عمیق Claude. نگاشت فعلی نویسنده (نام‌ها زود کهنه می‌شوند؛ از `orchestrator_capabilities` بخوانید): P-F = gpt-6-luna، P-W = gpt-6.1-sol، C-F = Haiku 5.5، C-W = Sonnet 5.5، C-D = Opus 5.5.

| UI: سیستم طراحی جدید یا landing | P-W | high | xhigh | C-W high | تصمیم‌های بصری گسترده بودجه را توجیه می‌کند |

| رمزها، زیرساخت production، کار بازگشت‌ناپذیر | فقط thread اصلی | — | — | اگر پیش‌نیاز نیست توقف | هرگز واگذار نمی‌شود |

**انتخاب effort:**

۱. اول دریچه‌های ایمنی (شروط council، ردیف‌های فقط thread اصلی)، بعد effort شروع ردیف. اندازه و زبان هرگز بر پیامد غلبه نمی‌کنند. برای حالت بازگشت‌ناپذیر یا مشترک یک پله بالاتر شروع کنید؛ برای spec دقیق یک پله پایین‌تر.
۲. یک نردبان کیفیت. «شکست» یعنی بررسی پذیرش رد شود یا نتیجه spec را نقض کند. spec غلط یا مبهم: spec را اصلاح و با همان effort دوباره اجرا کنید. شکست استدلالی: یک پله effort بالاتر روی همان مدل، با فرضیهٔ تازه. شکست دوم: یک تلاش روی جایگزین. سوم: thread اصلی. شکست ابزار/محیط جدا شمرده می‌شود.
۳. در دسترس بودن جدا از کیفیت است: provider خراب را رد کنید، نزدیک‌ترین ردیف Claude را بگیرید و کف کیفیت و قاعدهٔ بازبینی میان‌خانواده را حفظ کنید.
۴. `xhigh` یک خط دلیل می‌خواهد. `max`، `ultra`، `ultrathink`، `ultracode`، حالت fast و سطح سرویس priority خاموش‌اند مگر خودتان بخواهید (priority فقط وقتی منتظر فرزند مسیر بحرانی هستید).
۵. با شواهد تنظیم کنید: اگر ردیفی سه بار پشت‌سرهم بار اول پاس شد، effort شروعش را یک پله کم کنید؛ اگر سه بار پشت‌سرهم ارتقا لازم داشت، یک پله زیاد کنید. هر تغییر را در [LOG.md](../../t3-routing/LOG.md) ثبت کنید.
